# Risk Register

This register details the top technical and architectural risks for CGL Hustle Phase 0, along with mitigations.

| Risk ID | Risk Description | Impact | Owner | Mitigation Strategy |
| :-- | :--- | :--- | :--- | :--- |
| RR-01 | **Cross-project FK limitation (GK LLM separation)** | Inability to use strict database foreign keys for `question_id` because GK LLM content lives in a separate project/database, leading to potential orphaned records or data integrity issues. | Backend Architecture Team | Use application-level ingestion/snapshotting. `question_snapshots` caches the content immutably locally. Validation is performed via ingestion logic. `question_id` is treated strictly as an external reference contract. |
| RR-02 | **Clock skew exploitation** | Malicious actors or severely out-of-sync devices could manipulate client timestamps to force data overwrites during conflict resolution. | Security / Backend Team | Server applies a strict `tolerance_ms` boundary (3000ms). If drift exceeds this boundary, time-based tie-breaking is skipped entirely, defaulting to the immutable, chronologically-sortable ULID lexical tie-breaker. |
| RR-03 | **Sync race bursts (multiple devices syncing simultaneously)** | Two devices coming online at the exact same moment could cause race conditions in the DB, bypassing idempotency checks or mutating the same row concurrently. | Backend Team | Implement Postgres concurrency locks (`pg_advisory_xact_lock`) scoped to the specific `user_id`, `session_id`, and `question_id` inside the sync RPCs, ensuring serial execution of concurrent writes. |
| RR-04 | **RLS misconfiguration** | Errors in Row Level Security policies could expose one tenant's quiz data or PII to another. | Security / QA | Strict enforcement of `WITH CHECK (auth.uid() = user_id)` on all `INSERT` and `UPDATE` statements. No anonymous access allowed. Thorough automated testing of policies across tenant boundaries. |
| RR-05 | **Outbox growth/unbounded retries** | Chronic network failures or permanent 5xx server errors could cause the local Room sync queue to grow indefinitely, consuming storage and draining battery via WorkManager. | Android / Client Team | WorkManager exponential backoff limits retry frequency. After 24h, automatic background retries halt; state remains retryable via foreground reconciliation (user-triggered). Unrecoverable client errors (4xx) immediately drop the payload to a dead-letter queue. |
